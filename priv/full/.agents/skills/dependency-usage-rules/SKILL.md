# Dependency Rules

When adding or changing a Hex dependency:

1. **Inspect the exact version.** `mix hex.info <pkg>` for what is current,
   `mix.lock` for what is installed. They are different questions.
2. **Read the package-authored usage rules.**
   `docs/guides/dependency-rules.md` is the index — generated by
   `mix usage_rules.sync` from the `usage-rules.md` files our dependencies
   ship, and drift-checked by `mix precommit`. `mix usage_rules.list` shows
   the **declared** dependencies that ship rules; it does not show the
   transitive ones, and five of those ship rules too. `ls deps/*/usage-rules.md`
   is the full inventory.
3. **Inspect the exact docs.** `mix usage_rules.search_docs "<query>" -p <pkg>`
   searches hexdocs *at the installed version*, and
   `mix usage_rules.docs Module.fun/1` prints a module, function or arity.
   Both beat recalling an API from training data, which is how this repository
   acquired a `new AbstractMesh`.
4. **Inspect the changelog and the advisories.** `mix hex.audit`, `osv-scanner`.
5. **Add the project-specific constraints**, and say why in `mix.exs` beside
   the dependency rather than in a commit message nobody will find.

Two habits this repository learned the hard way: a distribution package is not
the current version, and newest is not always right — `@types/node` belongs on
the runtime's major, not on npm's `latest`. See CLAUDE.md §Versions.

UsageRules-generated guidance is authoritative for package mechanics; the product
project rules override generic suggestions.
